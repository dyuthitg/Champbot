## 1. What "good enough to publish" means

A comment is good enough to auto-schedule if it clears every **blocker** rule (§2) and a human reviewer, reading the source post, would recognize it as engaging with *this* person's actual point — not a shape that would fit under any post in the topic.

## 3. Where v1 and the shipped code disagreed, and what v2 does about each

A standing standard has to pick one number, not leave two documents contradicting each other. Three places v1 (drafted before any of this was measured against a real gate) and the code that actually shipped since don't match:

- **R2, length cap: v1 proposed 280 characters. The gate has enforced 400 since before this document existed, with no incident traced to the extra 120 characters.** v2 adopts **400** as the standing number — the production value, not the proposal — because v1's own justification for the number (length doesn't discriminate quality in the audit data) argues against re-tightening it without new evidence, not for it.
- **R6/R7, emoji and exclamation marks: v1 asked for a hard zero/one. The gate allows up to 2 emoji / 2 exclamation marks before warning, and treats the first over that as advisory only.** v2 does **not** resolve this — tightening it is a real behavior change to a live gate, which is Hemang's call per the ownership split in `COMMENT_RULES_ENFORCEMENT_GAP.md`, not mine to ship unilaterally inside a documentation pass. Logged as an open item, owner Hemang, due at the 2026-10-01 review.
- **R1, sentence count: never enforced as a blocker, only ever advisory.** Same status as above — needs new parsing logic in `check_copy()`, not a spec change. Owner Hemang, due 2026-10-01.

- **Ships today, no code change:** this document itself, as the standing reference, replacing v1's draft status.
- **Needs Hemang and a booked slot before the numbers in §2/§3 change again:** the R1 sentence-count check, and any decision to tighten R6/R7 to match v1's original ask.

## 5. Brand voice: what v1 proposed vs. what actually shipped
